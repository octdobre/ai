The software behind LLMs

Take away the chat window and an LLM is software you can download, start and send text to. It has two parts: a program that runs it, and a database produced by training, called the model.

The engine and the model

Many programs can run LLM models. One example is llama.cpp, written in C++. It's the engine of the LLM: it loads a model and does the calculations. Nothing in its code knows French, Python or history. Swap the model and the same engine behaves differently.

The model is a database of numbers called weights. Llama 2 70B has 70 billion of them at 2 bytes each, which makes a 140 GB file. Unlike an ordinary database, it holds no sentences or facts you could look up, only the numbers that training left behind.

The code is short. The behaviour is in the data.

From training to a running instance

The weights are set during a training process, which ends with a final model file. That file is fed into llama.cpp, which starts an instance of the model. You can then send it input text, and the model returns output text.

Tokens

The model doesn't see text. It understands tokens: words or pieces of words, each with an ID number. “Unbelievable” might become “Un”, “believ” and “able”. The engine encodes your input into an array of these numbers and decodes the numbers that come back. Llama 2 knows 32,000 different tokens.

The system prompt, the chat history and your question are all joined into that one array, like an SQL query built by joining strings. That is why prompt injection exists: nothing in the array separates instructions from data.

A statistical guess

Based on its trained weights, the model predicts which tokens are likely to follow your input and returns them in encoded form. The reply is a statistical guess at what the next tokens are.

So when you ask a question, the answer depends on two factors:

  • How the model was trained: what data it saw and how well the training went.
  • The quality of the model: its parameter size, meaning how many weights it has, and its quantization, meaning how far those weights were rounded to fit a smaller file.

Depending on these, the answer can be accurate or extremely imprecise. An imprecise answer presented as fact is what's now called a hallucination.

The main loop

Replies come from an ordinary loop. Each run of the neural network is called a forward pass:

python · simplified
weights = load("model.gguf")              # read-only from here on
tokens  = tokenize(prompt)

while len(tokens) < context_limit:
    probs = forward(weights, tokens)      # the neural network
    next  = sample(probs, temperature)    # pick one, with some randomness
    if next == END_TOKEN:
        break
    tokens.append(next)
    print(detokenize(next))               # stream it to the user

Replies appear word by word because each iteration yields one token, and APIs charge per token because the token is the unit of work.

Inside forward, nearly all of the work is matrix multiplication, which is why this software runs best on GPUs. No branch depends on what the input means. A tax question and a poem run the same instructions in the same order, and only the numbers differ.

No state, no side effects

Across calls, an LLM keeps nothing. The weights are read-only, and your next message works only because the host program sends the whole conversation again.

The model also makes no system calls. It can't open a file, reach the network or read the clock. When it “searches the web”, it has written text naming a tool and its arguments. A host program decides whether to run that tool and adds the result to the token array. All permissions and all effects on the world live in the host.

The build

Training is a separate program, and the closest analogy is a build. It reads text, predicts the next token, measures the error, nudges the weights and repeats billions of times. Andrej Karpathy called this Software 2.0: programs written as weights instead of by hand.

Unlike a compiler, which preserves what you wrote, training is a search: you supply examples and can't say exactly what will come out. Compare two releases and you get billions of changed numbers, with no readable diff.

Failure and debugging

The forward pass has no error path for not knowing something. It always returns valid probabilities, so the sampler always gets a token. A hallucination is therefore a successful execution: no exception, no warning, nothing in the logs.

A stack trace shows only matrix multiplication, and there's no line to patch, so the fixes are further training or a different input. Teams test with evals: hundreds of scored inputs, reported as a pass rate.

The stack around it

What people call “the AI” in a chat app is several layers of conventional software with the weights at the bottom.
